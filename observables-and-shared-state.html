    5. Observables and Shared State

    5.1. Example 19: Observables RxJS

    We’ve already encountered two types of values that change over time: signals, which always have a current value, and promises, which deliver a single value at a later time. [Angular] uses a third type: observables, provided by the [RxJS] library. An observable is a stream of values that arrive over time: keystrokes, timer ticks, router events (Example 17), a server’s response (Example 22).

    Their power lies in their operators: functions that transform one stream into another (filtering, waiting, discarding an expired request, etc.). This example presents the main ones in three scenarios.

    // =========================================================================
// 19-rxjs/src/app/app.ts - observables from the RxJS library
// -------------------------------------------------------------------------
// A OBSERVABLE is a FLUX of values that arrive over time (the
// keyboard keystrokes, the ticking of a timer, a server's response...).
// Angular makes extensive use of them: the client HTTP (Example 22) and the router
// (Example 17) return observables.
//    - observable.subscribe (function): we subscribe to ABONNE; the function receives
//      each value. Nothing happens until someone subscribes;
//    - observable.pipe(op1, op2...): a NOUVEAU stream, transformed by
//      OPÉRATEURS (map, filter, debounceTime, switchMap...) ;
//    - toSignal (observable): a signal whose value is the last received value
//      (automatic subscription and unsubscription).
// =========================================================================

import { Component, DestroyRef, inject, signal } from '@angular/core';
import { takeUntilDestroyed, toSignal } from '@angular/core/rxjs-interop';
import { debounceTime, delay, distinctUntilChanged, filter, interval, map, Observable, of, Subject, switchMap, take, tap } from 'rxjs';

const MEDECINS = ['Marie PELISSIER', 'Paul TATOU', 'Sophie DUPONT', 'Jacques DURAND', 'Martine PELLETIER'];

@Component({
  selector: 'app-root',
  templateUrl: './app.html',
})
export class App {
  protected readonly journal = signal<string[]>([]);

   // 2. a timer: 0, 1, 2... every second; take(20): 20 values
   // then the stream ends; map: each value is transformed
  private readonly secondes$ = interval(1000).pipe(
    take(20),
    map((n) => 20 - n - 1),
  );
   // toSignal: the countdown, in the form of a signal
  protected readonly rebours = toSignal(this.secondes$, { initialValue: 20 });

   // 3. A "real-time" search: a Subject is an observable
   // in which one POUSSE generates values (next) oneself
  private readonly saisies = new Subject<string>();
  protected readonly resultats = toSignal(
    this.saisies.pipe(
      map((texte) => texte.trim().toLowerCase()),
      debounceTime(400), // we wait 400 ms without any keystrokes
      distinctUntilChanged(), // text identical to the previous one is ignored
      filter((texte) => texte.length >= 2),
      tap((texte) => this.tracer(`recherche envoyée : « ${texte} »`)),
       // switchMap: a text search; if new text arrives
       // before the response, the previous search is ABANDONNÉE
      switchMap((texte) => this.rechercher(texte)),
    ),
    { initialValue: [] as string[] },
  );

  constructor() {
     // 1. A manually created observable: it emits three values, then terminates
    const troisValeurs = new Observable<string>((abonne) => {
      abonne.next('un');
      abonne.next('deux');
      setTimeout(() => {
        abonne.next('trois (une seconde plus tard)');
        abonne.complete();
      }, 1000);
    });
     // takeUntilDestroyed: the subscription ends if the component disappears
    troisValeurs.pipe(takeUntilDestroyed(inject(DestroyRef))).subscribe({
      next: (valeur) => this.tracer(`reçu : ${valeur}`),
      complete: () => this.tracer('flux terminé'),
    });
  }

  protected saisir(texte: string): void {
    this.saisies.next(texte);
  }

   // A simulated “server”: the response arrives after a random delay
  private rechercher(texte: string): Observable<string[]> {
    const trouves = MEDECINS.filter((m) => m.toLowerCase().includes(texte));
    return of(trouves).pipe(delay(200 + Math.random() * 600));
  }

  private tracer(message: string): void {
    this.journal.update((j) => [...j, `${new Date().toLocaleTimeString()} ${message}`]);
  }
}
    • line 18: the functions and operators used are all imported from [rxjs];

    A hand-built observable:

    • lines 57–64: An observable is constructed from a function, which is called for each subscriber. It emits values using [next] (lines 58, 59, 61), then signals the end of the stream using [complete] (line 62);
    • line 66: [subscribe]: the user subscribes to the stream. Nothing happens until someone subscribes: the function in lines 57–64 is executed only at that point. The object passed to [subscribe] specifies what to do with each value (line 67) and with the end of the stream (line 68);
    • line 66: [pipe] chains together operators. [takeUntilDestroyed] stops the subscription if the component disappears: a forgotten subscription would continue to run for a component that no longer exists.

    A countdown:

    • Line 31: [interval(1000)] transmits 0, 1, 2... every second, indefinitely;
    • Line 32: [take(20)] keeps only the first twenty values, then terminates the stream;
    • line 33: [map] transforms each value: 0, 1, 2... become 19, 18, 17...;
    • line 36: [toSignal] converts the stream into a signal, which is set to the last received value, and which the template reads like any other signal. [toSignal] subscribes to the stream and unsubscribes when the component disappears. [initialValue]: the value of the signal before the first value in the stream.

    By convention, the name of a variable that contains an observable ends with [$] (line 31).

    A search as you type:

    This is a classic example of observables: we want to search for doctors whose names contain the text being typed, without sending a request to the server with every keystroke, and without risking a slow response overwriting a more recent one.

    • Line 40: a ***[Subject] is an observable into which we *push values ourselves, using ***[next]***: line 73, with each keystroke (the template calls [saisir] for every [input] event);
    • line 43: the text is cleared;
    • line 44: [debounceTime(400)] only outputs a value if no other value arrives for 400 ms: as long as the user is typing, nothing is sent;
    • line 45: [distinctUntilChanged] ignores a value identical to the previous one (“pel,” then “pelx” immediately deleted: “pel” again);
    • line 46: [filter] retains only text strings of at least two letters;
    • line 47: [tap] performs an action without modifying the stream: in this case, a line in the log;
    • line 50: [switchMap] replaces each text with the result of its search (lines 77–80: a simulated server that responds after a random delay). If a new text arrives before the response, the previous search is abandoned: its response will never be displayed. With the real client HTTP, the request would even be canceled;
    • line 52: the [resultats] signal is an empty list as long as no search has been successful.

    Signals or observables? Both coexist in [Angular], with different roles:

     
    Signal
    Observable
    Value
    always has a current value, which can be read at any time
    emits values over time; no “current” value
    Usage
    the application's state (what is displayed)
    events and asynchronous operations (requests, timers, keystrokes)
    Subscription
    automatic (templates, [computed], [effect])
    explicit ([subscribe]), or via [toSignal]
    Key features
    Simplicity
    Operators: wait, combine, abandon

    The trend in [Angular] is to store the state in signals and to reserve observables for cases where their operators are useful. [toSignal] and [toObservable] alternate between the two. In the case study, the HTTP requests will be converted to promises ([firstValueFrom], Example 22), and the state will be encapsulated in signals; only router events will be listened to as observables.

    5.2. Example 20: A Shared State

    Several components often need the same data: the logged-in user (the navigation bar, guards, pages), messages to display, and the selected language. Where should this data be stored? The [NestJS] course addressed the same question on the server side (application, request, and session scopes). This example adapts it to the browser, with three “scopes”:

    • the local state of a component, stored in its own variables: it disappears when the component is destroyed;
    • the state of a root service: shared by all components, it survives their removal but not a page reload (F5), which restarts the application;
    • the state stored in the browser’s localStorage: it survives a page reload and even the closure of the browser.

    // =========================================================================
// 20-status-share/src/app/status/panier.service.ts - a ÉTAT PARTAGÉ
// -------------------------------------------------------------------------
// A root service (providedIn: 'root') that contains signals is a
// "store": UN—a single instance for the entire application, which
// all components share. Typical organization:
//    - the ÉTAT: signals PRIVÉS, which can only be modified by the service;
//    - signals in LECTURE SEULE (asReadonly) and computed signals, read by
//      the components;
//    - methods (the “actions”), which are the only ones that can modify the state.
// The service lives as long as the application does: it survives the removal of a
// component... but not a page reload (F5), which restarts
// the application. (No need for additional libraries, such as Pinia
// for Vue.js: services and signals are sufficient.)
// =========================================================================

import { computed, Injectable, signal } from '@angular/core';

export interface Article {
  libelle: string;
  prix: number;
}

@Injectable({ providedIn: 'root' })
export class PanierService {
  private readonly _articles = signal<Article[]>([]);

  readonly articles = this._articles.asReadonly();
  readonly nombre = computed(() => this._articles().length);
  readonly total = computed(() => this._articles().reduce((s, a) => s + a.prix, 0));

  ajouter(article: Article): void {
    this._articles.update((a) => [...a, article]);
  }

  vider(): void {
    this._articles.set([]);
  }
}

    A root service containing signals acts as a store ([store]): a single instance, shared by the entire application. It is organized into three parts:

    • line 26: the state, in a private signal: no component can modify it directly;
    • lines 28–30: what the components read: the read-only state ([asReadonly]) and calculated values ([computed]);
    • lines 32–38: the actions, the only methods that can modify the state.

    This approach has a key benefit: when a shopping cart is invalid, the only possible modifications occur within the service methods. With [Vue.js], a library ([Pinia]) is typically used for this purpose; with [Angular], services and signals alone suffice.

    // =========================================================================
// 20-state-sharing/src/app/state/preferences.service.ts - a state that survives F5
// -------------------------------------------------------------------------
// To ensure that data survives a page reload or when the
// the browser, it must be stored DANS in the browser: localStorage (a
// small key-to-string dictionary, unique to each site).
//    - on startup, the service re-reads localStorage;
//    - a function rewrites localStorage with every change.
// No sensitive data (passwords, tokens) is stored there: any script
// on the page can read localStorage.
// =========================================================================

import { effect, Injectable, signal } from '@angular/core';

const CLE = 'exemple20.preferences';

export interface Preferences {
  sombre: boolean;
  taille: number; // text size, in px
}

function lire(): Preferences {
  try {
    return { sombre: false, taille: 16, ...JSON.parse(localStorage.getItem(CLE) ?? '{}') };
  } catch {
    return { sombre: false, taille: 16 }; // unreadable content: default values
  }
}

@Injectable({ providedIn: 'root' })
export class PreferencesService {
  readonly preferences = signal<Preferences>(lire());

  constructor() {
    effect(() => localStorage.setItem(CLE, JSON.stringify(this.preferences())));
  }

   // A preference changes: the object is replaced (the signal detects this)
  modifier(changement: Partial<Preferences>): void {
    this.preferences.update((p) => ({ ...p, ...changement }));
  }
}
    • line 15: the key under which preferences are stored in [localStorage], a small key-to-string dictionary specific to each site;
    • lines 22–28: Upon startup, the saved preferences are read. The default values are supplemented by those that have been saved (using the [...] operator); unreadable content is ignored (line 26);
    • line 32: the preferences, in a signal;
    • line 35: an effect (example 13) rewrites the [localStorage] whenever the signal changes: you don’t have to think about it in every action;
    • lines 39–41: the action that modifies one or more preferences ([Partial<Preferences>]: an object where every property is optional). We replace the object rather than modifying it: a signal only detects changes in value.

    Sensitive data (passwords, login tokens) is never stored in the [localStorage]: any script executed by the page can read it. This is why the login token for the [RdvMedecins] application will be stored in a cookie, which is inaccessible to the [JavaScript] code.
